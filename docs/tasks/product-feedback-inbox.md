# 阶段 0：产品反馈收件箱

## 1. 目标

让用户可以不打分、用自然语言报告“哪里不对或看不懂”，并能看见处理进度；让作者能依据页面上下文分诊、记录处理说明和发布版本，而不是在平铺卡片中手工猜测。

## 2. 范围

- [ ] `/suggestions` 改为“问题与建议”：类型优先、自然语言输入、自动带入页面和设备上下文、用户可查看自己的处理进度。
- [ ] 扩展既有 `AuthorFeedback`，保留旧评分和历史数据，补充类型、页面上下文、作者说明、发布版本和更新时间。
- [ ] 作者后台的“意见反馈”改为反馈收件箱：类型/状态筛选、待分诊/待复现/已计划/已发布/暂不处理状态、作者说明与版本记录。
- [ ] 将学习周报的用户文案改为“周复盘”；支持作者页仍只处理支持留言。
- [ ] 增加用户提交、上下文保存、作者更新和用户回看的 Playwright 覆盖。

## 3. 非目标

- 不做用户与作者的即时聊天、工单指派、多作者协作或附件上传。
- 不把真实用户反馈公开给其他用户。
- 不迁移或删除现有 `AuthorFeedback`、`Feedback`（周复盘）或 `Supporter` 数据。
- 不把 Markdown 反馈台变成线上数据库；它只记录已分诊的产品决策。

## 4. 验收条件

- [ ] 登录用户可不选择星级，报告“问题 / 看不懂 / 建议 / 表扬 / 其他”之一，并提交一段描述。
- [ ] 反馈自动记录来源页面和安全的设备摘要；用户提交后可看到自己的处理状态与作者说明。
- [ ] 作者可按类型和状态定位反馈，更新状态、说明和发布版本；非管理员不能读取或更新他人反馈。
- [ ] 旧的 `new/read/resolved` 记录仍可显示并被继续处理。
- [ ] `/feedback` 明确为学习周复盘，不再被误解为向作者报告产品问题。
- [ ] 手机端提交和查看状态不横向溢出，主要操作不小于触控尺寸。

## 5. 测试范围

- [ ] `suggestions.spec.ts`：无评分提交、来源上下文、用户状态回看、手机布局。
- [ ] `admin.spec.ts`：非管理员 403；管理员状态更新（若存在可控管理员测试环境）。
- [ ] TypeScript、相关 ESLint；发布候选再跑生产构建与完整 E2E。
- [ ] Schema 变更使用兼容性迁移；生产 `prisma db push` 只在明确部署时执行。

## 6. 开工约束

- 目标分支：`dev`（当前工作分支）。
- 新增依赖：否。
- 涉及 Schema：是；所有新增列须有默认值或可空，旧记录继续可读。
